# O15 — Occupant Override & HMI Signal Model

> **Status: draft-for-review** (KG sprint 1, 2026-10-23). Filled to the ML-KG-04 fields; not `specified` until the owner has reviewed it (MLM SPECS2 §12). Closes SG-O15-1 and the O15 part of SG-LAYER-1 (mlm-library SPEC_GAPS.md; library D-28). Items marked **OWNER DECISION** are proposals; see REVIEW.md.

## Purpose
Merges automated, governed dispatch with manual occupant commands from the HMI (thermostat, app, physical button), so the occupant is always obeyed within equipment and safety limits (FLEXUS FX-GOV-05), and records override statistics that tell the RD layer how often and for how long automation is overridden.

## Layer
**Stochastic** — the merge itself is a deterministic priority rule; the stochastic output is the estimated override rate and duration distribution per household, used by [[O03]] and [[C08]].

---

## Formula

### LaTeX
Command sources in priority order (highest first): $\mathcal{S}$ = safety ([[C10]] safety block: storm or failed deterministic check), occupant (HMI), automatic ([[C10]]-governed [[C01]] output). For each asset and time $t$:
$$u_{final}(t) = \operatorname{clip}_{[u_{min}, u_{max}]}\Big( \text{command of the highest-priority source active at } t \Big)$$
i.e. the previous note's $u_{final}(t) = override\_signal(t) \oplus u_{auto}(t)$ with $\oplus$ defined as
$$a \oplus b = \begin{cases} a & a \text{ active} \\ b & \text{otherwise} \end{cases}$$
**Active occupant command:** each new occupant command for an asset *replaces* the previous one; it is active on $[t_{start},\, t_{start} + D)$ unless cancelled earlier:
$$override\_active(t) = \exists\, c:\; c \text{ is the latest occupant command for the asset},\; t_{start}(c) \le t < t_{start}(c) + D(c),\; \lnot cancelled(c)$$
**Override statistics** (trailing 30 days, occupied time only):
$$\hat\lambda_{ovr} = \frac{n_{overrides}}{H_{occupied}} \;[\text{h}^{-1}], \qquad \bar{D} = \frac{1}{n}\sum_c D_{effective}(c) \;[\text{min}]$$

### Description
Three sources can command an asset. Safety comes first: if C10 blocks for a storm or a failed deterministic check, the asset goes to its safe state whatever the occupant asked. The occupant comes next: their command holds for its duration (60 min by default) and overrides automation, including an RD-based derate or block (occupant choice beats flexibility, but not safety). Otherwise the governed automatic command applies. A new occupant command replaces the previous one for the same asset, as a later write to the same priority slot does in building automation; when it ends or is cancelled, control returns to automation, not to an older occupant command. This is the command-prioritisation scheme of BACnet commandable objects (ASHRAE 135), reduced to three levels. Override commands are typed with units: a setpoint (°C) is passed to C01 as a tracking band, a power command (W) or a mode (`off`, `boost`, `hold`) replaces the automatic power command. The final value is clipped to the asset's limits. The previous note left ⊕, overlapping overrides and the unit of `override_signal` undefined (SG-O15-1).

### Python Pseudocode
```python
from dataclasses import dataclass

@dataclass
class Command:
    asset: str
    kind: str          # 'setpoint' (degC) | 'power' (W) | 'mode' ('off', 'boost', 'hold')
    value: object
    t_start: float     # minutes
    duration: float = 60.0
    cancelled_at: float | None = None

def active(c, t):
    end = c.t_start + c.duration if c.cancelled_at is None else min(c.t_start + c.duration, c.cancelled_at)
    return c.t_start <= t < end

def o15_merge(t, asset, u_governed, safety_block, occupant_cmds, limits, mode_power):
    """occupant_cmds: all occupant commands for the asset, any order."""
    if safety_block:
        return limits.safe_state, 'safety', False
    started = [c for c in occupant_cmds if c.t_start <= t]
    latest = max(started, key=lambda c: c.t_start, default=None)   # replaces earlier ones
    if latest is not None and active(latest, t):
        if latest.kind == 'setpoint':
            return ('track', latest.value), 'occupant', True   # C01 tracking band
        u = latest.value if latest.kind == 'power' else mode_power[latest.value]
        return min(max(u, limits.u_min), limits.u_max), 'occupant', True
    return min(max(u_governed, limits.u_min), limits.u_max), 'automatic', False
```

## Method
Priority-based command arbitration with relinquish on expiry, as in the command prioritisation of BACnet commandable objects (ANSI/ASHRAE Standard 135, BACnet), here with three levels (safety, occupant, automatic). Override rate as a Poisson rate estimate per occupied hour; durations summarised empirically.

## RD Role
Stochastic layer, RD lifecycle steps 6–7. While an occupant command is active, the asset's flexibility is not available: RD for that asset is zero for the override's duration. Over longer horizons the override rate and duration give the expected unavailability, $1 - e^{-\hat\lambda_{ovr} K \Delta t}$ for an activation of $K$ steps under a Poisson model, which C08 applies as a human-factor discount alongside O03's comfort-driven probability. Every override is logged as RD human-factor evidence (FX-GOV-05).

---

## Validity Limits
- Three priority levels only; site-specific interlocks (e.g. legionella cycles) must be modelled as safety commands.
- The Poisson override model assumes overrides occur independently at a constant rate; overrides cluster around activations and in cold spells, so λ should be estimated separately for activation and non-activation periods once data allow.
- Setpoint tracking depends on C01 accepting a temporary band; if C01 cannot meet it, the local thermostat controls.
